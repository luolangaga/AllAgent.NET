### B01：升级后旧数据不可见

位置：[DataStore.cs:41](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Data/DataStore.cs:41)、[TerminalArguments.cs:53](C:/Users/luolan/LanAgent/src/AllAgent.NET.Terminal/TerminalArguments.cs:53)。

默认共享目录从 `LanAgent` 改为 `AllAgent`，项目目录从 `.lanagent` 改为 `.allagent`，数据库从 `lanagent.json` 改为 `allagent.json`。加载只查新名称，没有旧名称发现/迁移步骤。即使 `--data-dir` 显式指向旧目录，旧文件名仍不会读取；旧文件尚在，却显示空会话和空配置。原 v2→v3 迁移只能在已经找到数据库文件后生效，不能解决这个问题。

复现：创建一份有效数据库，将主/备份清单改回旧文件名，重新用 DataStore 打开同目录，结果 `visibleConversations = 0`、`oldManifestExists = true`。旧会话修订文件仍保留。

建议：首次启动先检测旧共享/项目目录和主备文件，在进程锁内执行可恢复迁移，保留原数据；处理新旧目录同时存在的情况，避免以空库覆盖旧库。目录索引、凭据、技能和插件路径需要一起定义迁移策略。

### B02：保存配置与实际发送配置不一致

### B03：一次协议拒绝让 UI 提前解除运行状态

位置：[BridgeHandlerRegistrar.cs:513](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Bridge/BridgeHandlerRegistrar.cs:513)、[conversations.ts:213](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/stores/conversations.ts:213)、[AgentEngine.cs:319](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Services/AgentEngine.cs:319)。

模型直接调用 `file_read` 等函数而没有使用 execute_code 时，Engine 发出 `ToolCallRejected`、记录失败结果，然后允许模型纠正；达到连续违规阈值才结束。桥接却把第一次拒绝也映射为 `agent.error`。React 的 onError 随即移除全部流监听并清空 activeStreamId，后续纠正回答、工具执行和 done 事件均被丢弃。UI 无法停止仍在运行的后端，还会允许用户再次发送，遇到后端“already has an active run”。

复现已确认后端映射为 agent.error；前端收到相同事件后，后续 token 不再显示。

建议：协议拒绝使用独立的非终止事件/notice；终止状态由确定的最终完成事件收口，并保留取消通道直到宿主真正退出运行。

### B04：会话加载覆盖新消息

位置：[conversations.ts:41](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/stores/conversations.ts:41)、[conversations.ts:89](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/stores/conversations.ts:89)、[Chat.tsx:84](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/views/Chat.tsx:84)。

选择会话会立即设置 activeId，再异步加载历史。输入框和 sendMessage 都没有阻止 isLoading 状态下发送，发送也没有让 selectionVersion 失效。因此历史响应晚到时会整体替换 messages；用户消息和已经生成的回复消失，而 streamingMessageId 仍非空。后续 token 找不到 assistantId，无法显示。

复现：挂起 getMessages/todos.get → 发送并接收 token → 返回旧历史；消息数量由 2 变为 0，流标记仍在。

建议：将加载和发送纳入同一会话操作状态机；加载完成前禁发，或发送时取消旧读取并合并有版本的快照。仅检查 activeId 不足以消除同会话竞态。

### B05：首次发送与新建会话互相覆盖

位置：[conversations.ts:47](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/stores/conversations.ts:47)、[App.tsx:39](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/App.tsx:39)。

sendMessage 在没有 activeId 时先等待 createConversation，此时内部 starting 已经为 true，但 streamingMessageId 还是 null。侧栏/快捷键只检查 streamingMessageId，createConversation 自身也不检查 starting，因此仍能第二次新建。第二个创建请求晚到后会切走 activeId、清空 messages，而第一个会话已经开始生成。

复现：挂起两个创建请求 → 第一个返回并启动流 → 第二个返回；activeId 变为 conv-2，消息为空，流标记仍在。任务继续在 conv-1 执行。

建议：让启动中状态可被所有会话操作读取；区分 send 内部确保会话存在与用户发起的新建操作，并验证异步返回时的操作版本。

### B06：插件 SDK 版本判断硬编码过期

位置：[NuGetPluginInstaller.cs:89](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Extensions/NuGetPluginInstaller.cs:89)、[AllAgent.NET.Core.csproj:8](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/AllAgent.NET.Core.csproj:8)。

Core 项目版本和运行程序集已经是 1.1.0，依赖校验却固定使用 `new NuGetVersion(1, 0, 0)`。依赖 `AllAgent.NET.Core [1.1.0,2.0.0)` 的当前插件会被拒绝；反过来，只接受 1.0.0 的窄范围可能被错误接受。

复现使用本地生成的最小 nupkg，不连接 NuGet、不加载插件 DLL。结果为宿主版本 1.1.0.0，却报“不兼容的 AllAgent.NET.Core SDK 版本”。

建议：使用明确维护的实际 SDK 契约版本或包版本，避免与程序集版本不一致；同时验证最低版本与排他上限。

### B07：Responses 错误格式使重试失效

位置：[ResponsesProvider.cs:104](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Services/AI/ResponsesProvider.cs:104)、[AgentEngine.cs:405](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Services/AgentEngine.cs:405)。

Responses 把 HTTP 错误转换成 `Responses 请求失败（HTTP 429）。`。Engine 将 ChunkType.Error 转为 InvalidOperationException，而瞬时错误正则要求 `^HTTP 429`/`^HTTP 5xx` 或几个特定关键词。该本地化字符串匹配不到，所以配置了 MaxModelRetries 也立即结束。HTTP 500/503 同样走这条不匹配路径。

复现：HTTP handler 固定返回 429、配置 2 次重试，实际请求只有 1 次。测试不访问网络。

建议：用带状态码的结构化异常/错误类型判断可重试性；不要依赖本地化错误文案。保留有界的服务端错误详情以支持图片拒绝诊断等恢复逻辑。

### B08：MCP 参数编辑显示成功但未生效

位置：[BridgeHandlerRegistrar.cs:459](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Bridge/BridgeHandlerRegistrar.cs:459)、[McpToolService.cs:245](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Services/McpToolService.cs:245)。

通过终端/导入配置保存过 ArgumentList 的服务，在桌面编辑参数时只更新 Arguments。连接代码优先取 ArgumentList，因此重连甚至重启仍使用旧数组。DTO 没有暴露这个优先级，页面显示新参数会造成误判。

复现：原 ArgumentList = ["old"]；通过 mcpServers.save 将 arguments 改为 "new"；数据库 Arguments 为 new，ArgumentList 仍为 ["old"]。

建议：统一以参数数组作为配置真值；旧字符串编辑入口应校验解析后更新数组，或明确清除旧数组。

### B09：内置技能开关与实际执行脱节

位置：[BridgeHandlerRegistrar.cs:301](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Bridge/BridgeHandlerRegistrar.cs:301)、[AgentRuntime.cs:26](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Runtime/AgentRuntime.cs:26)、[Management.tsx:74](C:/Users/luolan/LanAgent/src/AllAgent.NET.Web/src/views/Management.tsx:74)。

桌面页面承诺“管理 Agent 可以使用的技能”，并列出由 SystemTools 初始化的内置工具。开关只改 DataStore.Skills.IsEnabled。AgentRuntime 无条件注册 SystemTools，CodeAct 也没有读取这些标记；这里的 SkillCatalog 是读取 SKILL.md 的另一套机制。因此关闭 file_write 不能使实际 file_write 不可见或不可调用。

隔离验证：真实 RPC 把内置 file_write 标记设为 false，再按 Runtime 的相同方式注册 SystemTools；CodeAct 的模型目录仍含 file_write，调用仍写入测试文件。该验证覆盖注册与分发逻辑，没有实际打开桌面窗口。

建议：统一技能管理与当前运行时能力来源。若保留内置工具开关，应在可见目录和每次调用处执行同一启用策略；不能仅靠隐藏提示词。

### B10：断流后已显示回答丢失

位置：[AgentEngine.cs:206](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Services/AgentEngine.cs:206)、[AgentEngine.cs:282](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Services/AgentEngine.cs:282)。

token 先实时推送给 UI，只有完整模型响应通过后才 Save assistant。响应中途抛异常时直接进入错误结束流程，已收到的 content/thinking 没有落盘。重新选择会话或重启应用后，用户已经看过的部分回答消失，下一轮模型也不知道这段输出。

复现：Provider 先返回 "visible partial answer" 再抛 IOException。事件中确有该文字，DataStore 中 assistant 消息为空数组。取消发生在完整响应提交前也存在相同的保存缺口，但本次独立脚本只动态验证了断流。

建议：保存带 interrupted 状态的纯文本/思考片段；继续丢弃未完整提交的工具调用及不可验证的原生 provider state，防止把截断代码当成可执行请求。

### B11：空流也通过连接测试

位置：[BridgeHandlerRegistrar.cs:381](C:/Users/luolan/LanAgent/src/AllAgent.NET.Core/Bridge/BridgeHandlerRegistrar.cs:381)。

循环注释说至少消费一个有效 chunk 才算连接成功，但没有 observed-success 标记，Provider 一个 chunk 都不返回时依然执行循环后的 return true。该问题主要影响自定义/插件 Provider；内置协议通常会将不完整流转换成错误，因此优先级较低。

复现：注册空异步流 Provider，调用 apiConfigs.test，RPC 返回 data: true。

建议：明确记录至少收到 TextDelta/Done 后再返回成功；无输出结束应报“未收到有效响应”。

### B12：合法的同名工具类导致生成器崩溃

位置：[AgentToolGenerator.cs:62](C:/Users/luolan/LanAgent/src/AllAgent.NET.ToolGenerator/AgentToolGenerator.cs:62)。

生成器按完整类型分组，却用 `type.Name + ".AgentTools.g.cs"` 作为输出文件的唯一名称。如果同一程序集有 First.Tools 和 Second.Tools 两个工具类，它们本来是不同且合法的 public partial 类型，但输出名称都成为 Tools.AgentTools.g.cs。第二次 AddSource 抛出 ArgumentException，Roslyn 报 CS8785，生成器本轮的输出全部丢弃。

独立复现使用真实 AgentToolGenerator 和 Roslyn CSharpCompilation，两个工具名分别为 first/second；结果 `generatedTrees = 0`，错误明确提示 hintName 必须唯一。此问题不涉及重复的宿主工具名，也不需要运行任何工具。

建议：用经过文件名安全编码的完整类型标识（包括 namespace，必要时加稳定哈希）生成 hintName；为“不同 namespace、相同短类名”的合法输入增加编译验证。

## 测试基础设施与过期契约

终端集成测试从测试输出目录启动 `typeof(TerminalSession).Assembly.Location`。测试项目引用 Microsoft.AspNetCore.App，共享框架提供的依赖没有都复制到该目录，但拷贝来的 allagent.runtimeconfig.json 只声明 Microsoft.NETCore.App。单独执行这个 allagent.dll 时缺少 Microsoft.Extensions.Logging.Abstractions 10.0.0，多个真实终端测试在进入业务前失败或等待超时。

对照已实测：

- `dotnet src/AllAgent.NET.Terminal/bin/Debug/net10.0/allagent.dll providers list ... --json` 返回 `[]`。
- 同一命令改用 `tests/AllAgent.NET.Tests/bin/Debug/net10.0/allagent.dll`，报缺少 Logging.Abstractions。
- 给上述测试目录中的终端显式使用测试项目的 runtimeconfig 后，同一 providers list 命令恢复返回 `[]`，进一步确认是启动时共享框架声明与产物不一致。

这是测试启动产物问题，不能据此宣称正式 Terminal 构建无法启动。建议对子进程使用独立 build/publish 输出，并做运行依赖完整性检查。

另有明显契约漂移：BuiltinLoginTests 仍断言旧的动态客户端授权地址，当前代码已改成 native PKCE；NativeWebSearchTests 的一项仍要求旧的 HTTP 搜索回退，当前 WebTools 明确改用 Browser Use；ExecutionExperienceTests 仍要求默认非 FullAccess，当前默认已改为 FullAccess。这些失败应先确认产品意图，再更新测试或恢复契约，不能简单改期望让它们变绿。终端 Unicode 选区、表格选区和展示测试也有失败，尚未逐一证明根因，不计入上面的已定位产品问题数。

另三项失败与当前明确实现的契约冲突：SuccessfulRetryCompletesTheHostTurnWithStop 先输出文本再要求默认重试，而 RetryAfterModelOutput 默认是 false；FullAccessStillRejectsImportsAndRequiresSandbox 把主 worker 缺失等同于所有沙箱不可用，当前 Auto 模式会回退 Monty；CancellingDesktopParentAlsoCancelsItsChild 要求取消父任务连带取消子任务，而当前 subagent 工具契约明确说明已接纳的子任务继续在后台运行。这些都需要产品意图与测试同步，不能直接把安全策略或任务生命周期改回旧行为来满足测试。
